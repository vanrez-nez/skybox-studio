# shadcn/ui and tweakcn Setup Notes

This document records the setup path that avoids the issues we hit while wiring shadcn/ui, lucide, Tailwind v4, and a tweakcn theme into this Vite + React + TypeScript project.

References checked:

- shadcn Vite installation: https://ui.shadcn.com/docs/installation/vite
- shadcn CLI: https://ui.shadcn.com/docs/cli
- shadcn registry items: https://ui.shadcn.com/docs/registry/registry-item-json
- tweakcn repository: https://github.com/jnsahaj/tweakcn
- Lara theme page: https://tweakcn.com/themes/cmm2769u2000004jobride6q4

## Core Rule

Do not treat a tweakcn theme as a full UI kit.

A tweakcn theme install command like this:

```bash
npx shadcn@latest add https://tweakcn.com/r/themes/cmm2769u2000004jobride6q4
```

installs a shadcn registry style item. In practice, that means it updates CSS variables and theme tokens. It does not install the whole preview page, demo app, mail layout, tab wrapper components, or every component recipe used by tweakcn's showcase.

To match a tweakcn showcase, three things must line up:

1. The theme tokens from tweakcn.
2. The shadcn component recipe baseline.
3. The actual app/demo composition used in the showcase.

If any of those differ, the result can be valid shadcn UI, but it will not look identical to the screenshot.

## Install shadcn/ui in a Vite Project

For a new project, shadcn documents the Vite scaffold path as:

```bash
npx shadcn@latest init -t vite
```

For an existing Vite React TypeScript project, make sure these pieces exist before running shadcn:

```bash
npm install tailwindcss @tailwindcss/vite
npm install lucide-react
```

Configure the Vite alias so `@/` resolves to `src/`.

```ts
// vite.config.ts
import path from "path"
import tailwindcss from "@tailwindcss/vite"
import react from "@vitejs/plugin-react"
import { defineConfig } from "vite"

export default defineConfig({
  plugins: [react(), tailwindcss()],
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "./src"),
    },
  },
})
```

Then initialize shadcn:

```bash
npx shadcn@latest init
```

When prompted, choose the component baseline intentionally. For this project, use:

```json
{
  "style": "new-york",
  "tailwind": {
    "css": "src/styles.css",
    "baseColor": "neutral",
    "cssVariables": true
  },
  "iconLibrary": "lucide"
}
```

The `style` field matters. It controls the component source recipes generated by shadcn. If this is wrong, the theme can be installed correctly and the UI can still look wrong.

## Add Components

Add only the components the app actually uses:

```bash
npx shadcn@latest add button tabs menubar
```

In this project, `tabs`, `menubar`, and `button` are local source files under:

```text
src/components/ui/
```

shadcn/ui is not a black-box component package. The CLI copies component source into the repo. That means generated source can differ depending on `components.json`, CLI version, and selected component baseline.

## Install a tweakcn Theme

Run the exact tweakcn registry command from the theme page:

```bash
npx shadcn@latest add https://tweakcn.com/r/themes/cmm2769u2000004jobride6q4 -y
```

Expected result:

```text
Checking registry.
Updating src/styles.css
```

That output is normal for a `registry:style` theme. It does not mean the command failed. It means the registry item updated theme CSS.

## Correct CSS Shape

The global stylesheet should be theme-token driven. Do not patch colors manually to force a screenshot match.

A healthy Tailwind v4 + shadcn + tweakcn CSS file has this rough structure:

```css
@import "tailwindcss";
@import "tw-animate-css";

@custom-variant dark (&:is(.dark *));

:root {
  /* tweakcn light tokens */
}

@theme inline {
  /* Tailwind token mappings */
}

.dark {
  /* tweakcn dark tokens */
}

@layer base {
  * {
    @apply border-border outline-ring/50;
  }

  body {
    @apply bg-background text-foreground;
    letter-spacing: var(--tracking-normal);
  }

  html {
    @apply font-sans;
  }
}
```

Avoid keeping Vite starter styles or ad hoc global resets unless the app explicitly needs them. These commonly interfere with visual debugging:

```css
:root {
  color: ...;
  background: ...;
  font-family: ...;
}

body {
  min-width: ...;
  min-height: ...;
  overflow: hidden;
}

button {
  cursor: pointer;
}
```

If the theme defines `--background`, `--foreground`, `--muted`, `--secondary`, and other tokens, use those through shadcn/Tailwind classes. Do not add hard-coded background colors just to force the UI closer to a screenshot.

## Dark Mode

The dark theme only applies under the `.dark` class:

```html
<html lang="en" class="dark">
```

If the app is not in dark mode, the Lara dark showcase will not match. The theme can be installed correctly and still look wrong if `.dark` is missing.

## The Main Pitfall: Theme Tokens Are Not Component Recipes

The Lara mail preview on tweakcn is a full demo page. It uses:

- The Lara theme tokens.
- shadcn components.
- tweakcn's own app/demo composition.
- In some places, tweakcn-specific wrapper components, such as its preview tab pill trigger.

For example, the tweakcn preview shell uses `TabsTriggerPill` for the top preview tabs. That is not the same thing as default shadcn `<TabsTrigger>`.

The mail demo itself also contains layout and application-specific Tailwind classes for panels, sidebars, scroll areas, resizable panes, and selected mail items. A theme install cannot recreate that application structure.

Correct conclusion:

```text
Theme install + different markup = same colors, different UI.
Theme install + same component recipes + same markup = close visual match.
```

Incorrect conclusion:

```text
The theme command should make every arbitrary Tabs instance look exactly like the mail screenshot.
```

## Matching a tweakcn Showcase Properly

If the goal is to match a tweakcn showcase, do not inspect and copy screenshots. Use source or registry data.

Use this process:

1. Run the exact tweakcn theme command.
2. Confirm `components.json` uses the same shadcn baseline as the showcase source.
3. Add the shadcn components required by the UI.
4. If a component shape differs, compare against tweakcn's source, not the screenshot.
5. If the showcase uses a wrapper or demo component, import or recreate that source intentionally.
6. Keep app-level layout classes separate from component styling.

For this project, the important correction was:

```json
{
  "style": "new-york"
}
```

The earlier `radix-nova` baseline generated a different Tabs recipe. The Lara theme was present, but the component source did not match the tweakcn showcase baseline.

## What Not To Do

Do not merge random CSS from several generated states.

Do not add hard-coded fixes like:

```tsx
className="bg-[#111] text-white"
```

Do not assume the theme failed just because a component shape differs.

Do not repeatedly run `shadcn init` over an existing project without checking the diff. It can merge generated CSS into existing app CSS and leave duplicate or stale rules.

Do not use screenshot matching as the source of truth when the upstream implementation is available.

## Troubleshooting

### The theme installed, but tabs have no dark colors

Check:

- `src/styles.css` is imported from `src/main.tsx`.
- `index.html` or a theme provider applies `.dark`.
- The tweakcn token blocks exist in `:root` and `.dark`.
- The `@theme inline` block maps variables like `--color-background`, `--color-muted`, and `--color-foreground`.

### Tabs are colored but the shape is wrong

Check:

- `components.json` has the expected `style`.
- `src/components/ui/tabs.tsx` matches the expected component recipe.
- The app is using default `<TabsList>` and `<TabsTrigger>` without per-instance overrides.

### The tweakcn command only changed `styles.css`

That is expected for a theme registry item. It means the command applied theme tokens. It does not install showcase source.

### The preview screenshot has controls we do not have

That is app/demo composition, not theme. Find the source component in the tweakcn repo or install an official block/registry item if one exists.

## Verification

After changing shadcn config, component source, or theme CSS, run:

```bash
npm run build
```

For visual changes, also run the dev server and inspect the actual rendered page:

```bash
npm run dev
```

The goal is not to add custom styling until it looks close. The goal is to ensure the theme, shadcn baseline, and source composition are all aligned.
